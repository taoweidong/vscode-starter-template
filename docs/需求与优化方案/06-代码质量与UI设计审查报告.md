## 2. 代码质量审查

### 2.1 设计系统组件层（`src/webview/ui/`）

#### C-1 🔴 `VFormField` 模块级自增序号生成 id —— 改 `useId()`

**位置**：`src/webview/ui/VFormField.vue:3,29`

**问题**：`let fieldSeq = 0` + `ref('v-field-${++fieldSeq}')` 有三个隐患：① 模块级可变状态，HMR / 多测试用例间不复位，快照类测试不稳定；② 迫使 `eslint.config.ts:96-99` 为整个 `src/webview/ui/**` 关闭 `no-useless-assignment`——**为一行代码给整个目录开豁免**；③ `ref` 包裹永不变化的值，是无谓的响应式开销。

**优化思路**：Vue 3.5 已内置 `useId()`（项目 `vue ^3.5.44`），按应用实例隔离、SSR 安全、无模块状态。

```ts
// VFormField.vue
<script setup lang="ts">
import { computed, provide, useId } from 'vue'
// ...
// 旧：let fieldSeq = 0（模块级）+ ref(`v-field-${++fieldSeq}`）
const generatedId = useId() // 形如 "v-0"，每实例唯一且与 HMR/测试隔离
const controlId = computed(() => props.for ?? generatedId.value)
```

同时 `VInput.vue:28` / `VTextarea.vue:23` / `VSelect.vue:24` 的 `fallbackId = ref('v-input')` 是**固定字符串**——同一页面多个未包 `VFormField` 的实例会产生重复 DOM id（目前 gallery 有几个这样的裸 `VInput`，暂无 label 关联所以未爆，但属埋雷）。一并改 `useId()`：

```ts
// VInput.vue / VTextarea.vue / VSelect.vue
const fallbackId = useId() // 替代 ref('v-input') 固定串
```

**收益**：可删除 `eslint.config.ts` 中 `src/webview/ui/**` 的 `no-useless-assignment` 豁免（见 §2.6 E-1）。

#### C-2 🔴 `stripMeta` 的三个 `void _x` 语句是死代码

**位置**：`src/domain/itemSchema.ts:201-207`

**问题**：`eslint.config.ts:45-48` 已配置 `varsIgnorePattern: '^_'`，下划线前缀变量本就被 `no-unused-vars` 忽略，三个 `void` 语句纯属历史遗留。

```ts
// 优化后：直接删除三行 void
function stripMeta(item: Item & Record<string, unknown>): Record<string, unknown> {
  const { id: _id, createdAt: _createdAt, updatedAt: _updatedAt, ...rest } = item
  return rest
}
```

**位置**：`src/webview/ui/VCheckbox.vue:33-44`

**问题**：`VInput` / `VSelect` / `VTextarea` 都绑定了 `:aria-invalid="isInvalid || undefined"`，唯独 `VCheckbox` 没有——`VFormField` 的 invalid 上下文对布尔字段断裂。当前 5 个特性开关均非必填所以未暴露，属「一致性欠账」。

```vue
<input
  :id="controlId"
  class="v-checkbox__input"
  type="checkbox"
  :checked="modelValue"
  :disabled="disabled"
  :aria-invalid="field?.invalid.value || undefined"
  :aria-describedby="field?.describedBy.value"
  @change="onChange"
/>
```

#### C-4 🟡 空 `withDefaults(..., {})` 冗余

**位置**：`VBadge.vue:6-12`、`VEmptyState.vue:6-16`、`VLoading.vue:7-14`

**问题**：`withDefaults(defineProps<...>(...), {})` 传空对象不提供任何默认值，属噪声。直接删掉第二参数即可（`defineProps` 本身不需要 withDefaults 包裹）。

```ts

const props = defineProps<{ label?: string | number }>()
```

**问题**：`Required<Pick<WebviewControllerDeps, 'createPanel' | 'resolveAssets' | 'log'>> & WebviewControllerDeps` 依赖「required ∩ optional = required」的交叉规则，可读性差。

### 2.2 页面层（`src/webview/apps/` + `components/`）

#### C-6 🔴 `itemForm` 与 `featureConfig` 两页重复约 80 行表单编排逻辑 —— 提取 `useFormPage` composable

**位置**：`apps/itemForm/App.vue:64-212` vs `apps/featureConfig/App.vue:31-110`

**问题**：两页各自实现了同一套「宿主消息监听 → init 回填 → baseline/dirty → watch 上报 dirty → submit 在途 → submitAck/error 复位」流程，仅草稿持久化与错误展示粒度不同。第三、第四个表单页出现时将继续复制。

**优化思路**：抽 `src/webview/composables/useFormPage.ts`，两页只保留差异部分。

```ts
// src/webview/composables/useFormPage.ts（示意）
import { onBeforeUnmount, onMounted, ref, watch } from 'vue'
import { isHostMessage, type HostMessage } from '../protocol'
import { useVsCodeApi } from '../shared/useVsCodeApi'

export interface FormPageOptions {
  /** init 到达时的差异处理（草稿恢复等），返回是否已初始化 */
  onInit: (message: Extract<HostMessage, { type: 'init' }>) => void
  onError?: (message: Extract<HostMessage, { type: 'error' }>) => void
}

export function useFormPage(options: FormPageOptions) {
  const api = useVsCodeApi()
  const initialized = ref(false)
  const submitting = ref(false)
  const hostError = ref('')

  function onHostMessage(event: MessageEvent): void {
    const message = event.data
    if (!isHostMessage(message)) return
    switch (message.type) {
      case 'init':
        options.onInit(message)
        initialized.value = true
        break
      case 'submitAck':
        submitting.value = false
        hostError.value = ''
        break
      case 'error':
        submitting.value = false
        options.onError?.(message)
        break
      default:
        break
    }
  }

  onMounted(() => {
    window.addEventListener('message', onHostMessage)
    api.postMessage({ type: 'ready' })
  })
  onBeforeUnmount(() => window.removeEventListener('message', onHostMessage))

  return { initialized, submitting, hostError }
}
```

#### C-7 🟡 `dirty` 用 `JSON.stringify` 比较 —— 键序脆弱 + 每击键全量序列化

**位置**：`apps/itemForm/App.vue:58`、`apps/featureConfig/App.vue:29`

**问题**：① 正确性依赖「baseline 与 value 键序一致」的隐式契约——目前因二者同源派生而成立，但扩展字段 / 草稿恢复路径一旦出现键序差异即误判 dirty；② 长描述字段每次击键触发深度序列化。

**优化思路**：稳定序列化（按键排序）或限定已知字段浅比较。稳定序列化改动最小、对扩展字段同样正确：

```ts
// src/webview/shared/stableStringify.ts
/** 按键排序的稳定 JSON 序列化：dirty 比较不受对象键序影响。 */
export function stableStringify(value: unknown): string {
  if (value === null || typeof value !== 'object') return JSON.stringify(value) ?? 'null'
  if (Array.isArray(value)) return `[${value.map(stableStringify).join(',')}]`
  const entries = Object.entries(value as Record<string, unknown>).sort(([a], [b]) =>
    a < b ? -1 : a > b ? 1 : 0
  )
  return `{${entries.map(([k, v]) => `${JSON.stringify(k)}:${stableStringify(v)}`).join(',')}}`
}

// 页面内：const dirty = computed(() => stableStringify(value.value) !== stableStringify(baseline.value))
```

#### C-9 🟢 `Promise.resolve().then` 替代 `nextTick`

**位置**：`apps/itemForm/App.vue:143-145`

#### C-10 🟢 宿主错误不随输入清除

**位置**：`components/SchemaForm.vue:63-70`（`setValue` 只清 `localErrors`）

**问题**：宿主 `coerceDraft` 回传的字段错误（`props.errors`）在用户继续输入时仍然挂着，直到再次提交。本地错误已有「输入即清」，宿主错误应对齐。

```ts
function setValue(field: FormField, value: unknown): void {
  const next = { ...localErrors.value }
  delete next[field.key]
  localErrors.value = next
  // 宿主错误同样随输入清除（页面层 fieldErrors 由 emit 通知父级删除）
  if (props.errors[field.key] !== undefined) {
    emit('clearError', field.key)
  }
  emit('update:modelValue', { ...props.modelValue, [field.key]: value })
}
```

页面侧 `fieldErrors` 收到 `clearError` 后 `delete` 对应键即可。

### 2.3 宿主服务层（`services/` `models/` `domain/`）

#### C-11 🟡 `ItemService.list()` 每次过滤都重新拼接 + 全量 `toLowerCase`

**位置**：`src/services/itemService.ts:65-77`

**问题**：数据数百条时无感；按模板定位（数百至数千条）每次 `list()`（树刷新、视图状态更新都走它）都对全字段做 `join + toLowerCase + includes`，重复计算。

**优化思路**：缓存失效时预计算「搜索文本」，过滤只做 `includes`。

```ts
private searchTexts: string[] = [] // 与 cache 平行，persist/缓存命中时同步

private rebuildSearchIndex(items: Item[]): void {
  this.searchTexts = items.map((item) =>
    [item.name, item.category, item.description, item.tags.join(' ')].join(' ').toLowerCase()
  )
}

async list(): Promise<Item[]> {
  const items = await this.ensureLoaded()
  const keyword = this.filter.trim().toLowerCase()
  if (!keyword) return [...items]
  return items.filter((_, i) => this.searchTexts[i]?.includes(keyword))
}
```

> `ensureLoaded` 命缓存与 `persist` 两处调用 `rebuildSearchIndex`；`invalidate` 时清空。需同步补单测（`itemService.spec.ts` 有现成夹具）。

#### C-12 🟢 `escapeMarkdownInline` 漏转义反斜杠（真实小 bug）

**位置**：`src/commands/index.ts:612-615`

**问题**：条目名称/描述含 `\` 时，复制出的 Markdown 中 `\` 会被当作转义符，渲染错乱。转义必须先处理反斜杠自身。

```ts
/** Markdown 行内特殊字符转义（\ * _ [ ] `；反斜杠优先）。 */
function escapeMarkdownInline(text: string): string {
  return text.replace(/([\\*_`[\]])/g, '\\$1')
}
```

建议先在 `commands` 相关 spec 里补一条含 `\` 的用例再修（遵循「先写复现用例」协议）。

#### C-13 🟢 `toItemDraft` 的 `tags.map(String)` 绕过领域校验意图

### 3.3 交互体验

#### U-1 🔴 Esc / 点「取消」直接关闭，dirty 修改静默丢失

**位置**：`webview/host/webviewController.ts:303-306`（`case 'cancel'` 直接 `onCancel?.()`）

**问题**：`confirmSwitchTarget` 只保护了「切换目标」路径；用户在表单里改了一堆字、按 Esc 或点取消，面板直接 dispose，草稿持久化（itemForm 有 500ms 防抖 setState）能救回一部分，但 featureConfig 无草稿、且 itemForm 的防抖窗口内（<500ms）的修改仍会丢。这是唯一一条**数据丢失路径**，优先级最高。

**优化思路**：宿主在 cancel 分支复用确认逻辑，**协议零改**（页面无感知；用户拒绝时面板保持打开、状态原样）：

```ts
// webviewController.ts
case 'cancel':
  void this.handleCancel()
  break

private async handleCancel(): Promise<void> {
  if (this.dirty) {
    const discard = '放弃修改并关闭'
    const choice = await vscode.window.showWarningMessage(
      '当前有未保存的修改，关闭面板将丢失这些修改。',
      { modal: true },
      discard
    )
    if (choice !== discard) {
      return // 用户拒绝：面板保持打开，页面状态不变（可继续编辑后重新保存/取消）
    }
  }
  this.dirty = false
  this.deps.onCancel?.()
}
```

`dirty` 标志页面已实时上报（`{type:'dirty'}`），无需新增消息。需补单测：dirty=true 时 cancel → 弹确认 → 拒绝不 dispose / 同意才 dispose。

#### U-6 🟢 步骤条当前步可点击回跳缺失（importWizard）

### 6.3 环境备忘：`ELECTRON_RUN_AS_NODE=1` 会打断集成测试

集成测试曾全部失败于 `Code.exe: bad option: --disable-extensions`（exit 9），`.vscode-test` 缓存一度被误判为「下载产物损坏」。取证翻转：缓存中的 Code.exe 与本机正版安装的 VS Code 1.143.1 **字节级一致**（均 238,249,784 B，Electron 43.7.7 / Node 24），归档 3279 个文件与 zip 清单逐一吻合，缓存从未损坏。

真正根因：**Agent 宿主进程向工具会话注入了 `ELECTRON_RUN_AS_NODE=1`**（用于抑制 GUI 弹窗；User/Machine 作用域均无此变量），`@vscode/test-electron` spawn 的 Code.exe 继承该变量后以 Node 模式运行，拒绝所有 VS Code 应用参数。

处置：跑集成测试 / 门禁时剥掉该变量——

```bash
env -u ELECTRON_RUN_AS_NODE node out/test/runTest.js
```

另两条同类环境约束（本次实测）：vitest 需以小写盘符路径为 cwd（`/e/...`）运行，否则触发 ESM 双实例故障；coverage 目录清理会被 safe-delete 护栏拦截，需配合 `CODEBUDDY_SAFE_DELETE_ENABLED=0`。
