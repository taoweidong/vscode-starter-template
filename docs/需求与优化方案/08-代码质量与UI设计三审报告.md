## 3. 第三轮新发现

### F1 🟢（P2 · 环境）门禁在 WorkBuddy 沙箱内第⑦步需关闭 safe-delete 护栏

**证据**：不设置 `CODEBUDDY_SAFE_DELETE_ENABLED=0` 时，`npm run gate` 在 **第⑦步（vitest 覆盖率清理）** 抛 `Unhandled Error`：

```
[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":78,"threshold":50,
  "targets":["E:\\GitHub\\vscode-starter-template\\coverage\\.tmp"]...}
   ❯ V8CoverageProvider.cleanAfterRun ... rm ...
```

属 Agent 宿主 `node-safe-delete-shim` 对 >50 文件删除的 fail-closed 拦截（见 项目记忆）。**测试本身全部通过**，仅覆盖率临时目录清理被拦。加 `CODEBUDDY_SAFE_DELETE_ENABLED=0` 后第⑦步即绿，9/9 全过。

**影响**：本沙箱内无法裸跑 `npm run gate` 复现绿；非代码缺陷，是环境护栏与门禁工具链的交互。

**优化思路（不改代码，仅文档化）**：在 `agent.md` / README 的「门禁」小节注明本沙箱前缀：

```bash
CODEBUDDY_SAFE_DELETE_ENABLED=0 env -u ELECTRON_RUN_AS_NODE npm run gate
```

若希望门禁脚本自带韧性，可在 `gate.ts` 顶部 `process.env.CODEBUDDY_SAFE_DELETE_ENABLED = '0'`（覆盖式赋值，仅影响本进程），但需评估是否会误伤「确应拦截的大批量删除」场景——**倾向先文档化**。

### F2 🟡（P1 · gitignore 缺口）`.vscode/crud-starter.config.json` 未被忽略

**证据（本会话实测）**：工作树出现未跟踪文件 `.vscode/crud-starter.config.json`，内容为 `ensureDefault` 生成的**标准默认配置**（`"name":"CRUD Starter 示例项目","version":"0.4.0"`）。`.gitignore` 仅忽略 `.vscode/crud-starter-items.json`（第 11 行），**未忽略 `-config.json`**。

该文件一旦落入工作树，`prettier --check .`（门禁第①步）即对它报格式问题 → **门禁第①步失败**。本会话实测：删除该文件后第①步立即 `All matched files use Prettier code style!` 通过；保留时第①步失败。

**根因**：`.gitignore` 对待两类「插件生成的配置文件」不对称——数据文件 `*-items.json` 被忽略，静态配置默认文件 `*-config.json` 没有。

**优化思路（建议立即做，零风险）**：`.gitignore` 增补一行，与 `items.json` 对称：

```gitignore
# 插件生成的静态配置默认文件（ensureDefault 生成，非用户提交物）
.vscode/crud-starter.config.json
```

**验证**：增补后 `git status` 不再将其列为未跟踪；`prettier --check .` 对其免疫。

### F3 🟢（P2 · 可维护性）`KNOWN_DRAFT_KEYS` 与 `ITEM_FIELD_DEFS` 手工同步

**证据**：`itemFormPanel.ts` 的 R-C-2 引入两个手写集合：

```ts
const KNOWN_DRAFT_KEYS = new Set(['name', 'category', 'description', 'priority', 'tags'])
const META_KEYS = new Set(['id', 'createdAt', 'updatedAt'])
```

而 `src/domain/itemSchema.ts:81` 已存在单一来源范式：

```ts
const DEFINED_KEYS = new Set(ITEM_FIELD_DEFS.map((def) => def.key))
```

两者键集合当前一致，但 `KNOWN_DRAFT_KEYS` 属「手工镜像」——**新增字段时若只改 `ITEM_FIELD_DEFS`（单一来源），会漏改此处**，扩展字段透传语义静默失真（恰好违背 R-C-2 想守护的「加字段零改动」承诺）。

**优化思路**：从 `ITEM_FIELD_DEFS` 派生，消除镜像：

```ts
// itemFormPanel.ts
import { ITEM_FIELD_DEFS, toDraft } from '../domain/itemSchema'
// ……
const KNOWN_DRAFT_KEYS = new Set(ITEM_FIELD_DEFS.map((def) => def.key))
const META_KEYS = new Set(['id', 'createdAt', 'updatedAt']) // 系统元字段仍手写，仅 3 个，可接受
```

`itemFormPanel.ts` 已 `import { toDraft } from '../domain/itemSchema'`，无新增依赖、无循环依赖。

**验证**：单测不变；人工确认派生集合与原 `['name','category','description','priority','tags']` 一致（读取 `ITEM_FIELD_DEFS` 即可）。
