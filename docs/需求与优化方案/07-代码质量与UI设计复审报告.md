## 2. 重要澄清：CSP 与内联样式（实验取证，排除一项误报 P0）

并行复审中曾有「严格 CSP 阻止内联样式，导入向导进度条在真实宿主永不渲染」的 P0 判定。编排者用本机 Edge（Chromium 内核，与 VSCode Electron 同引擎）做了三组决定性实验（CSP 为 `style-src 'self'`，即无 `'unsafe-inline'`，与项目 `webviewHtml.ts:42` 同构）：

| 实验                                        | 结果            |
| ------------------------------------------- | --------------- |
| HTML `style="width: 111px"` **属性**        | ❌ 被拦截（空） |
| `el.style.width = '50px'`（CSSOM 直接赋值） | ✅ 50px 生效    |
| `el.style.cssText = 'width: 77px'`          | ✅ 77px 生效    |
| `el.style.setProperty('width', '88px')`     | ✅ 88px 生效    |

**结论**：CSP `style-src` 无 `'unsafe-inline'` 时，被拦截的是 **`style` 属性与 `<style>` 元素**；**CSSOM manipulation 不受影响**。Vue 的 `:style` 对象绑定编译产物是 `patchStyle` 逐键 `setProperty`/赋值（CSSOM），不是属性——**进度条填充在真实宿主中正常渲染，该 P0 不成立**。旁证：本机正版 VS Code 1.143.1 自带的 webview 模板（`e646868227/resources/app/out/vs/workbench/contrib/webview/browser/pre/index.html:8`）用的正是 `style-src 'unsafe-inline'`，说明其 UI 体系依赖内联样式能力；而本项目选择了更严格的策略且用法安全。

**但实验暴露出两个真实的残留风险**（转化为工程化建议）：

1. **源码中若出现静态 `style="..."` 属性，会被 CSP 静默拦截**（当前全仓 0 处，但无任何门禁或测试能发现——e2e harness `tests/e2e/server.mjs` 生成的页面不带 CSP meta）。→ 见 R-E-12（style.ts 增加静态属性扫描）与 R-E-11（harness 镜像真实 CSP）。
2. `docs/需求与优化方案/03:211` 写的「内联 `style` 属性（布局白名单除外）」具有误导性——CSP 不存在白名单机制。→ 文档修正，见 R-E-13。

### R-C-1 🟡 `list()` 用共享 `searchTexts` 按下标过滤，过期 load 结果会错杀/错放条目

**位置**：`src/services/itemService.ts:73`（list）、`:264`（invalidate 清空 searchTexts）、`:275-298`（ensureLoaded 过期返回）

**问题与根因**（✔ 本轮独立复核证实）：过滤是「用 `items` 数组下标索引另一份平行数组」：

```ts
// itemService.ts:73
return items.filter((_, index) => this.searchTexts[index]?.includes(keyword) ?? false)
```

`ensureLoaded()` 在世代过期时**只把过期 items 返回给本次调用方、不落缓存**（:285-289，这是第一轮修对的语义），但此时 `this.searchTexts` 属于另一世代（或已被 `invalidate()` 清空为 `[]`，:264）。于是过期调用方的 items 与 searchTexts 按下标错配：

- 新 load 未完成（`searchTexts === []`）：`?? false` 使**所有条目被滤掉**——树视图瞬间清空、徽标变 0；
- 新 load 先完成：用新数据文本判旧数据条目——**错放不匹配条目**。

现有 spec（`itemService.spec.ts:329-347`）只验证「过期结果不落缓存」，未覆盖过滤维度。

**优化思路**：让 items 与搜索文本同源同生命周期——`ensureLoaded` 返回快照对象：

```ts
// itemService.ts（示意）
private snapshot: { items: Item[]; searchTexts: string[] } | undefined

async list(): Promise<Item[]> {
  const { items, searchTexts } = await this.ensureLoaded()
  const keyword = this.filter.trim().toLowerCase()
  if (!keyword) return [...items]
  return items.filter((_, index) => searchTexts[index]?.includes(keyword) ?? false)
}

private async ensureLoaded(): Promise<{ items: Item[]; searchTexts: string[] }> {
  if (this.snapshot) return this.snapshot
  if (!this.loadPromise) {
    const generation = this.reloadGeneration
    this.loadPromise = this.store.load().then(
      (items) => {
        this.loadPromise = undefined
        const next = { items, searchTexts: buildSearchTexts(items) } // rebuildSearchIndex 提为模块函数
        if (generation === this.reloadGeneration) this.snapshot = next
        return next // 过期也整体返回，调用方自洽
      },
      (err) => { this.loadPromise = undefined; throw err }
    )
  }
  return this.loadPromise
}
```

`persist` 改为 `this.snapshot = { items: next, searchTexts: buildSearchTexts(next) }`；`invalidate()` 清 `snapshot`。

**验证**：`itemService.spec.ts` 补「`setFilter('甲')` 后挂起 load#1 → `reload()` → 挂起 load#2 → 先 resolve load#2 再 resolve load#1 → 两次 list() 均正确过滤」（当前实现下第一条得到 `[]`）。

### R-C-2 🟡 面板边界的 `toItemDraft` 白名单丢弃扩展字段——「加字段零改动」承诺在编辑链路断裂

**位置**：`src/providers/itemFormPanel.ts:253-265`（✔ 本轮独立复核证实）

**问题与根因**：第一轮把 field 透传根因修在了领域层与服务层，但页面提交进入宿主的第一站仍是硬编码白名单：

```ts
// itemFormPanel.ts:254-265
function toItemDraft(draft: Record<string, unknown>): ItemDraft {
  return {
    name: String(draft.name ?? ''),
    category: String(draft.category ?? ''),
    description: String(draft.description ?? ''),
    priority: (isPriority(draft.priority) ? draft.priority : 'medium') as Priority,
    tags: Array.isArray(draft.tags) ? draft.tags.filter(...) : [],
  } // ← 任何不在列表里的 key 到此为止
}
```

按 README 给 `ITEM_FIELD_DEFS` 加 `owner` 后：表单 Schema 派生 → 页面渲染 → 用户修改 → submit 的 draft 带 `owner` → **被 `toItemDraft` 丢弃** → `update()` 的 `{...items[index], ...input}` 用旧值合并（itemService.ts:149）→ 界面没变、也没报错，修改静默丢失。而 `target.initial` 路径反而保留扩展字段（itemFormPanel.ts:205），**同一文件内两种语义不一致**。

**优化思路**：已知字段做结构清洗，未知 key 原样放行，类型校验统一交给 `coerceDraft`（与「校验交给服务层」的注释名副其实）：

```ts
// itemFormPanel.ts（示意）
function toItemDraft(draft: Record<string, unknown>): ItemDraft {
  const result: Record<string, unknown> = {
    name: draft.name,
    category: draft.category,
    description: draft.description,
    priority: draft.priority,
    tags: draft.tags,
  }
  const KNOWN = new Set(['name', 'category', 'description', 'priority', 'tags'])
  const META = new Set(['id', 'createdAt', 'updatedAt'])
  for (const [key, value] of Object.entries(draft)) {
    if (!KNOWN.has(key) && !META.has(key)) result[key] = value // 扩展字段透传
  }
  return result as ItemDraft
}
```

> 注：顺带消除 R-C-14（`String(draft.name)` 把对象 name 预清洗成 `"[object Object]"` 绕过必填校验）。

**验证**：`panels/itemFormPanel.spec.ts` 补「submit draft 带 `owner` → `service.update` 收到的对象 `owner === '李四'`」；与 `regression.spec.ts` 合起来闭合「领域→服务→面板」全链条。

### R-C-3 🟡 数据文件损坏后每次 load 都重新备份 + 重新弹模态，可形成「弹窗风暴」

**位置**：`src/services/stores/jsonFileStore.ts:135-157`（recoverFromCorruption）、`src/services/itemService.ts:291-294`（load 失败清 loadPromise）、`src/extension.ts:40-54`（onCorrupted 三选一）

**问题与根因**：`ensureLoaded` 失败分支清空 `loadPromise` 且不缓存错误，下次任何读取都重新走 `store.load()`；而损坏路径每次都会 `JSON.parse` 失败 → 再 copy 一份带时间戳的备份 → 再调 `onCorrupted` 弹模态。用户关掉恢复弹窗（返回 `abort`）后，每次点树视图、每条命令都会再弹一次，并在目录里堆积 `*.corrupt-<ts>.bak`——从「一次明确的事故」变成「持续骚扰 + 磁盘垃圾」。

**优化思路**：把「损坏」按文件缓存为终态，直到文件内容变化才允许重试：

```ts
// JsonFileStore（示意）：同一文件的连续损坏只恢复一次
private lastCorruption: { at: number } | undefined

private async recoverFromCorruption(reason: string): Promise<Item[]> {
  const now = Date.now()
  if (this.lastCorruption && now - this.lastCorruption.at < CORRUPTION_RETRY_WINDOW_MS) {
    throw new StoreCorruptedError({ ...this.lastInfo, reason }) // 复用 info，不重复备份/不重复问
  }
  this.lastCorruption = { at: now }
  // …原恢复逻辑…
}
```

**验证**：`jsonFileStore.spec.ts` 补「连续两次 load 只备份一次、只问一次」（注入 onCorrupted 计数）。

**位置**：`src/features/build/buildService.ts:37`（`DEFAULT_DIRTY_IGNORES`）、`:179`（预留的 `dirtyIgnorePrefixes` 选项）、`src/extension.ts`（组装处未接线）（✔ 本轮独立复核证实：extension.ts 全无 `dirtyIgnorePrefixes` 引用）

### R-C-5 🟢 watcher 自写抑制按「时间窗」而非因果关系，会吞掉保存前瞬间的真实外部修改

**位置**：`src/services/storageController.ts:174-182`（✔ 本轮独立复核证实）

**问题与根因**：抑制条件是定时器触发时的 `Date.now() - lastPersistAt < 500`，而非事件产生时刻与保存时刻的因果对比。用户 t=0 手工编辑文件、插件 t=50 保存、t=300 定时器触发时 `250 < 500` → 判自身写入 → 丢弃——但该事件携带的是用户的真实编辑。

**优化思路**：记录事件到达时间做因果判定：

```ts
// storageController.ts（示意）
private scheduleExternalReload(): void {
  if (!this.shouldAutoReload() || this.reloadTimer) return
  const eventAt = Date.now() // 事件产生时刻，而非定时器触发时刻
  this.reloadTimer = setTimeout(() => {
    this.reloadTimer = undefined
    const lastPersistAt = this.service.lastPersistAt
    // 事件早于最近一次保存 → 可能是自身写入回声；晚于保存 → 真实外部修改
    if (lastPersistAt !== undefined && eventAt < lastPersistAt) return
    this.service.reload()
  }, RELOAD_DEBOUNCE_MS)
}
```

**验证**：`storageController.spec.ts` 补「事件在保存前到达 → 抑制；事件在保存后到达 → reload」一对用例。

### R-C-10 🟢 submit 10 秒超时与业务任务竞态：超时报错后任务可能已落盘，或落败后重试造成重复创建

**位置**：`src/webview/host/webviewController.ts:372-409`（handleSubmit 的 `Promise.race`）

**问题与根因**：超时分支 reject 后发 error 并解锁，但 `onSubmit(draft)` 指向的任务**没有被取消**：任务随后成功时，面板内部已 `onClose()` + 成功提示——用户同时看到「超时错误」和「已新增」；用户重试则 `create` 非幂等 → 重复条目。现有 spec 无超时路径用例。

**优化思路**：倾向前者——超时仅告警，最终响应以任务落定为准：

```ts
// webviewController.ts（示意）
try {
  await Promise.race([task, timeout])
  this.post({ type: 'submitAck', ok: true })
} catch (err) {
  if (err instanceof SubmitTimeoutError) {
    this.deps.log('提交超时，等待业务任务落定；面板不关闭')
    await task.then(
      () => this.post({ type: 'submitAck', ok: true }), // 迟到的成功也如实告知
      (e: unknown) => this.postError(e)
    )
  } else {
    this.postError(err)
  }
}
```

**验证**：`webviewController.spec.ts` 补「onSubmit 慢于 10s」用例（假时钟）：超时窗口内不发 error、任务 resolve 后发 submitAck、面板不关闭。

### R-U-1 🟡 TagsField 的回显 watch 吞掉尾随分隔符，逗号分隔输入被系统性破坏

**位置**：`src/webview/components/fields/TagsField.vue:24-33`（✔ 本轮独立复核证实）

**问题与根因**：

```ts
watch(
  () => props.modelValue,
  (value) => {
    const joined = joinTags(value)
    if (joined !== text.value) {
      // ← 文本相等判定
      text.value = joined
      tags.value = parseTags(joined)
    }
  }
)
```

用户每输入一个分隔符，`parseTags` 丢弃空项 → emit 的数组语义不变，但父级 `setValue` 传入新引用对象（SchemaForm.vue:77 `{...props.modelValue, [field.key]: value}`）→ watch 必然触发 → `joinTags(解析结果)` 短于用户当前文本（缺尾逗号）→ **用户刚输入的分隔符被回显值覆盖删除**。英文逗号逐字符输入「前端, 待办」会得到「前端 待办」一个词；中文输入法上屏「，」同样被吞。e2e 用 `fill('前端, 待办')` 一次性设值，恰好绕开该路径。

**优化思路**：watch 以「解析语义相等」而非「文本相等」作为覆盖条件：

```ts
// TagsField.vue
watch(
  () => props.modelValue,
  (value) => {
    const externalTags = parseTags(joinTags(value))
    // 语义相等（逐项相同）时保留用户当前文本：不吞尾随分隔符，也不打断 IME 组合
    const same =
      externalTags.length === tags.value.length &&
      externalTags.every((tag, index) => tag === tags.value[index])
    if (!same) {
      text.value = joinTags(value)
      tags.value = externalTags
    }
  }
)
```

**验证**：e2e `pressSequentially('前端,')` 后 100ms 内断言值不被重置；回归「编辑回填显示 `a, b`」「草稿恢复显示 `a, b`」现有断言。

}

### R-E-4 🟡 `style.ts` import 白名单存在绕过（副作用 import 不被检查）

**位置**：`scripts/checks/style.ts:123`（正则强制要求 `from '...'`）

**问题与根因**：① 副作用 import `import '@vscode/codicons/dist/codicon.css'`（`apps/*/main.ts:5` 的真实写法）不含 `from`，**完全不被匹配**——当下能过仅因漏匹配而非命中白名单；② 跨行 import、`export ... from`、动态 `import('x')` 同样漏匹配；③ 白名单是精确等于 `@vscode/codicons`，真实用的是子路径，若有人写成带 `from` 的子路径导入反而被误报。即 04 §9.3 承诺的「禁 UI 框架导入」可被一条无 `from` 的副作用 import 绕过。

**优化思路**：改为包名前缀白名单 + 覆盖全部 import 形式：

```ts
// scripts/checks/style.ts（示意）
function pkgName(spec: string): string | null {
  if (spec.startsWith('.') || spec.startsWith('/')) return null // 相对/绝对路径放行
  const clean = spec.replace(/[?#].*$/, '')
  const parts = clean.split('/')
  return clean.startsWith('@') ? parts.slice(0, 2).join('/') : parts[0]
}
const ALLOWED_PKG = new Set(['vue', '@vscode/codicons'])
// 匹配副作用 / 多行 / 动态 / export-from 全部形态
const IMPORT_RE =
  /(?:import|export)\s+(?:[^'"]*?\s*from\s*)?['"]([^'"]+)['"]|\bimport\s*\(\s*['"]([^'"]+)['"]\s*\)/gs
```

### 10.5 本轮踩坑（可复用）

1. **jsdom 的 `focus()` 三要素**：① 组件必须 `attachTo` 真实挂载点（未 attach 时 `isConnected=false`，
   jsdom 直接放弃 focus）；② 元素需可解析的 `tabindex`；③ `watch → nextTick → focus` 发生在
   `flushJobs` **之后**的微任务里，比 `vi.waitFor` 的首次检查晚一拍 —— 焦点断言必须也用 `waitFor`，
   不能即时断言。三者缺一都会表现成「focus 无效」。
2. **门禁规则升级必须反向验证**：升级规则 4 后注入 `gap: 16px`（升级前合法）与
   `#probe-app` / `url(#gradient)` / `content: "#123"`（升级前误报）逐一确认「该红的红、不该红的没红」；
   否则「门禁通过」只说明规则没生效。
3. **`--vscode-*` 令牌泄漏一处**：`VCheckbox` 的 `accent-color` 直接消费 `--vscode-checkbox-select-background`，
   绕开了「组件只消费 `--ui-*`」的层。已登记 `--ui-check-selected` 并切换 —— 这也让 e2e 主题能 100% 从
   tokens.css 解析（否则要额外兜底名单）。
4. **429 限流下的半成品**：`server.mjs` 留下两个未使用变量（`randomBytes` / `CSP_ORIGIN`）——
   只写了声明没接线，且 eslint 会红。**门禁第 ① 步是发现这类半成品最便宜的手段。**
